# 多智能体讨论室：MVP 设计

2026-11-23 · 已确认范围，尚未实现。资料和竞品对照见[调研文档](research.md)。

## 1. 产品规则

- 一个讨论室属于一个 OpenChamber 项目。房主可加入已有会话，也可按角色新建独立 OpenCode 会话。新会话使用当前工作区、默认完全权限；已有会话保留原有权限与工作区。首版不建 worktree、不改全局权限设置。创建页明确提示新会话的执行权限和共享工作区的写入冲突风险。
- 一个会话同一时间可加入一个活跃讨论室。首条真人议题启动讨论；建房和加人不启动模型。成员可发言、反驳、补证据，或不回复。分工用帖子表达，不做任务表、锁或固定协调者。
- 人类和 agent 的讨论帖都发给其他所有当前成员。发送者自己的帖直接记为已读，不唤醒自己。普通帖排队；`@成员` 对点名者用 `steer`，其他人照样收到并排队；`@all` 对其他全员用 `steer`。提及改变送达时机，不改变可见范围。
- 首版只轮转文本、引用和消息链接。工具调用、流式碎片、私有会话内容、已读和系统状态不自动变成群帖，也不会唤醒其他 agent。Agent 通过房间工具主动发帖，普通会话最终回复不自动转发。
- 关闭 UI 不停止后台分发；手动暂停或用尽配额才暂停投递。待答问题、讨论记录和待投递任务均可在服务重启后恢复。

## 2. 唤醒与预算

| 收件人状态 | 普通贴 | 被 `@` 或命中 `@all` |
| --- | --- | --- |
| 空闲 | 提交 `delivery: "queue"` 并安排执行 | 提交 `delivery: "steer"` 并安排执行 |
| 正在跑 | 独立于其他成员排队，本轮结束后送入 | 在下一可接收边界插入，不承诺打断运行中的工具 |
| 房间已暂停 | 持久化待投递，继续后按序合批 | 同样记账；继续时保留 `steer` 意图 |
| 会话不可达 | 只重试该收件人，不阻塞其他人 | 同左；UI 显示待投递或异常 |

### 合批与顺序

1. 一次发帖事务写入消息、不可变的房间序号和收件人待投递记录。提交即向发帖方返回，不等收件人。
2. 按接收会话自然合批，**不设固定合并窗**。空闲即发送；忙碌时普通帖留在房间队列。若收到点名，按房间序号从最早未提交的帖子组批，尽可能把该收件人的全部积压一起送入 `steer`，较早的普通帖放在点名帖之前。每条保留独立 ID、引用与回执。
3. **同一个收件人的后帖不越过前帖。** 批次正文装不下时，先送较早的连续一批，后续保留 `steer` 意图；宁可让点名稍晚，也不跳过旧帖。如果较早的房间批已被 OpenCode 接纳但仍待投递，后续房间批先留在本地，待确认旧批投递且能从会话记录定位后再继续。每位收件人只允许一个尚未确认投递的批次；不撤回、不复制已接纳消息。结果未知就暂停该成员的分发并核对，不拿新 ID 绕过。这里保证的是本房间向同一会话的投递顺序，不保证不同成员同时收到，也不重排用户在该会话手动提交的其他输入。
4. 输入包含作者、消息 ID、引用、正文或有标记的截断，以及原始帖子链接。只把真正呈现的正文计为已读；截断片段、未包含的较长消息可通过历史工具取全文。
5. 提及通过明确的房间成员 ID 解析；UI 提及选择器和 agent 工具都使用结构化目标。正文引用、代码块里的 `@`、对旧帖的引用不会再触发。发帖者，含 `@all` 的发帖者，不投递给自己。

**预算**：每个房间每段默认 **50 次自动唤醒**。一次是向一个 agent 提交一个已接纳的批；一批中四条帖仍只算一次，给四个 agent 则算四次。新增轮次和同轮 `steer` 都消耗一次；人类阅读、传输重试、本地历史查询不计。并发分发前原子预留，接纳后核销，明确未接纳则释放；不能用新 ID 重试一条结果未知的投递来绕过预算。

达到 50 次暂停，人工点继续后开启新的 **50 次**。手动暂停沿用同一套恢复语义。暂停仍可发帖、回答、撤回和查看；恢复时从每个成员积压合批。暂停不取消已成功提交给 OpenCode 的工作，也不终止正在运行的会话。UI 显示「自动唤醒 7 / 50」、暂停原因及待补投情况。投递记录注明收件成员和这批包含的帖子数，便于理解扣次。`@all` 不绕过预算。

## 3. 群内异步提问

### 提问、答复、撤回

`room_ask` 立即返回问题 ID 和帖子 ID。调用不挂住本轮，也不创建一个原生 OpenCode 表单来等待；agent 可继续做其他事或结束本轮。现有的 OpenCode 提问组件只作为题干、选项、补充说明的交互参考。

问题卡片是一条真正的房间帖：所有成员都能查看、补充、指出问题已有答案，或协商哪一位撤回重复问题。状态为 `pending`、`answered`、`withdrawn`。MVP 支持文本作答和单选（可带补充文字）；不自动判重，不自动把同伴普通回复变成真人答案。

- **回答**：真人在问题卡片上显式回答，将答案写为引用原帖的群消息，同一事务将问题置为已答。仍广播给其他成员；提问 agent 附加 `steer`，无需真人再手输 `@`。
- **撤回**：仅提问者自己或房主可撤回待答问题，可注明“已有答案”并引用消息，或注明与哪个问题重复。其他 agent 用普通帖协商，没有代替对方撤回的权限。撤回标记保留，问题从待答列表移除。
- **竞争**：回答和撤回用条件更新，只接受先成功提交的状态变更；界面收到冲突后刷新，不自动重新提交。撤回若已胜出，迟到的观点可作为普通引用帖发送，不触发提问者的额外 `steer`。即使房间暂停，也可更新问题状态；实际唤醒等人工继续。

### 人类工作台

一个 OpenChamber 全屏扩展页包含独立的**房间聊天**和**待回答问题**两栏。待答栏保留自己的筛选、选中项、滚动位置；聊天栏保留自己的滚动位置和草稿。点击一个问题只改变聊天栏的消息锚点：加载前后消息，突出原帖，可原地回答。允许跨本项目房间跳转时，待答栏仍保留原状态。手机窄屏可在同一页面切换两栏，切回恢复状态。MVP 不做两个 OS 窗口。

房间顶部显示参与者、运行/等待/不可达提示、预算与暂停开关。消息可引用、复制定位链接或打开已读详情；为 agent 角色提供跳转到对应独立会话的入口。切到历史位置时，不因新帖自动滚到底。

## 4. 历史、定位和飞书式已读

### 历史查询语义

每条消息有稳定 `messageId` 和单调递增 `roomSeq`。历史按序号做游标分页，不用偏移量；新帖不会让已经读过的页漂移。引用保存原 ID，不复制整段正文。

| Agent 工具 | 典型使用 | 返回 |
| --- | --- | --- |
| `room_history` | 看最近记录；按人类或 agent 过滤；从上次游标接着看 | 有界消息列表（默认 20、最多 50）；作者 ID/类型/显示名、序号、时间、文本或摘要、引用、问题简态；不返回已读名单 |
| `room_context` | 打开一条消息当时的上下文 | 锚点全文与按房间原序排列的前后邻居；默认各 5 条。即使由作者筛选页打开，也显示其他作者的同期回复 |
| `room_readers` | 显式查一条消息有哪些人和 agent 已读 | 指定消息的已读成员列表及时间；有分页，不随历史列表或上下文附带 |
| `room_post` / `room_ask` / `room_withdraw_question` | 发帖、异步提问、撤回自己的问题 | 已写入的 ID 和状态，不等待广播或回答 |

`room_history` 默认查最新一页，支持向早/晚翻页及作者过滤；游标绑定房间和筛选条件。长文本超过返回额度时带 `truncated`，通过 `room_context` 定位，不让一条长日志挤掉整批消息。读取按稳定成员 ID 查询；改显示名不改变历史归属。新加入的成员可以回看房间历史，自动投递从加入后的首帖开始；不会因为加入就将所有历史算成已读或触发一轮。

### 什么算“已读”

| 动作 | 记为 |
| --- | --- |
| 房间已持久化，或 OpenCode inbox 已接纳 | 已记录／已接纳，不是已读 |
| agent 的这条正文进入实际提交给模型的一轮上下文 | 已读；须用公开可观测边界验证，不能拿入队事件代替 |
| agent 调用历史工具，工具结果向该轮呈现该条完整正文 | 已读；看见摘要、定位链接或 `room_readers` 列表不算 |
| 人类在可见窗口内打开正文 | 已读；初版以消息正文在可见栏中达到约半面积、停留 500ms 为实现起点。隐藏标签、仅加载的记录和待答侧栏摘要不算 |
| 作者成功发出自己的帖子 | 只对作者标记已读，不唤醒作者 |

UI 采用类似飞书的消息详情：点击一条帖的已读入口，按人类和 agent 分组查看。因作者过滤、跳读或手动读旧帖，已读不可假设为连续前缀；按 `(messageId, memberId)` 幂等存回执。真实“理解了”不可观测。若目标版本没有能确认上下文呈现的信号，UI 只报“已接纳”或“已投递”，不把它伪装成已读；主动查阅全文的回执仍可按已验证路径记录。

## 5. 模块与持久化

| 模块 | 职责 |
| --- | --- |
| **OpenChamber 扩展** | 房间 UI、成员选择和权限说明、聊天/待答双栏、历史和已读入口。按扩展能力显式安装服务端插件。OpenCode 客户端 UI 插件不能当成 OpenChamber 页面使用。 |
| **OpenCode V2 服务端插件** | 注册 agent 工具和类型化 RPC，识别调用来源会话，按 `queue` / `steer` 投递会话输入。房间不是系统指令；投递保留真实成员出处、结构化 ID，隔离聊天内容与控制动作。 |
| **房间服务** | 单一持久化写入点及分发器，负责帖子、问题、成员授权、回执、重试和预算；允许 UI 关闭后运行。已用临时受控 loopback 通道验证同机的扩展服务与插件互通。正式接入需定义持久队列的领取和确认、通道配置及重启恢复；OpenChamber 的只读 OpenCode 代理不能提交消息，投递由插件执行。 |

建议持久化用本地 SQLite，需先验证扩展宿主的数据目录及驱动可用性。核心记录：

- `rooms`、`members`：项目和房间状态、预算批次；成员身份分开保存人类与 OpenCode 会话。停用或离开会停止未提交的待投递，不抹掉历史归属。
- `messages`、`questions`：发帖与引用、房间内顺序、提及与问题状态，问题状态和回答/撤回引用一起提交。
- `outbox`、`delivery_batches`：每位接收者的待投递记录、预算批次和尝试状态。对投递批生成可重用的 OpenCode 输入 ID。V2.3.2 实测同一服务进程内同 ID 重试不会重复投递，但已送达项的重试响应可能回显新时间和新模式，原始值以本地记录为准。跨重启仍须验证；提交结果未知时优先核对 inbox/消息记录，不能核对就显示“投递结果不明”。
- `read_receipts`：每条消息每个成员的首次呈现时间、来源。UI 实时事件只作刷新提示，断线后从快照/游标补齐，不能依赖实时流重放。

使用已验证的成员身份，不允许模型自报 `senderId`、真人答复、伪造回执或调用房主操作。完全权限是新会话执行策略，不改变房间成员边界。除房间里的显式文本外，不主动向同伴公开私有会话、凭据或工具输出。

## 6. 实施前验证与验收

**先做接口冒烟，再做闭环。** [OpenChamber SDK](https://docs.openchamber.dev/sdk) 支持全屏页和随扩展安装 OpenCode 插件；[Host API](https://docs.openchamber.dev/sdk/host) 有后台服务与会话事件。[OpenCode V2 服务端插件](https://opencode.ai/docs/build/plugins/server)、[插件 RPC](https://opencode.ai/docs/build/plugins/rpc)与 [OpenAPI](https://opencode.ai/docs/openapi.json) 提供会话创建、提交、inbox 和事件接口。文档确认有能力，不代表部署版本已验证。尤其要验证：

1. 新建会话能否单独应用完全权限而不修改现有会话或全局设置。若目标接口不支持，UI 必须明示，不能悄悄开启全局自动授权。
2. [V2.3.2 已用独立服务和模拟模型实测](opencode-delivery-probe.md)：`queue` 可唤醒空闲会话；忙碌时 `steer` 在工具续跑边界进入，且可越过 `queue`；同进程内同 ID 重试不重复投递。不要用会关闭待答表单的 OpenChamber `sessions.send` 偷做 `steer`。MVP 不设计原生审批流程；如果目标会话意外在等原生输入，不代答、不关掉它，不让它阻塞全房间。
3. 实测已确认 `session.inbox.delivered` 和 `context` hook 都发生在模型确认收到前。尚需验证跨协议的模型响应关联、历史工具呈现、扩展关闭后的服务持续运行，以及重启后积压恢复。缺少可靠回执时按“已投递”降级。

**验收场景**：

- 三个独立会话进入同一房间。人类首帖叫醒三者；A 普通发帖，B、C 都拿到。A 点名 B 时，忙碌的 B 在同轮下个边界拿到，C 普通排队。`@all` 对其他成员生效，A 不自醒。
- 成员忙碌期间收到普通帖，再收到点名帖，两条按原顺序合成一次 `steer`，无需等待固定窗口。较早的房间批已经进入 inbox 但未到达时，点名帖不能越过它。一位会话离线或运行失败，不影响其他人。中途重启服务，帖子和积压仍在；已接纳的批不静默重复。
- 第 50 次接纳后停止自动投递；暂停期间允许人发帖和回答。继续后取得新 50 次，按成员补投积压，不漏帖。
- A 问人后可退出当前轮；B 可在群里指出重复并协商。A 撤回后卡片保留但离开待答列表。真人回答另一问题后，A 按规则被唤醒，其他人也收到答案。点击待答问题时，问题列表的滚动和筛选保持不变。
- 按不同作者翻历史并返回某一条时，看得到同期上下文；仅入队不出现在已读名单。显式查某一条可以分辨人类和 agent；`room_history` 与 `room_context` 不带已读名单。

不纳入 MVP：跨项目房间、多用户租户、自动工单分配、自动查重、文件附件、跨机器房间联邦、审批工作流和研究领域特化工具。采用普通代码设计评审或小型数学讨论来验证协作效果，不把“能跑模型”当作“协作有收益”。

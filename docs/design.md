# 多智能体讨论室：MVP 设计

2026-11-23 · 已确认范围。实现状态、运行方式和当前边界见 [README](../README.md)。资料和竞品对照见[调研文档](research.md)。

## 1. 产品规则

- 一个讨论室属于一个 OpenChamber 项目。房主在创建页选定项目、成员角色和模型；系统为各 Agent 生成可编辑的默认显示名，房主可在确认建房前修改。确认后先创建一个不调用模型的房间根会话，再为每个成员自动创建独立的 OpenCode 会话。成员通过 OpenChamber `operator-child` metadata 逻辑关联到根会话，作为子会话显示在根会话下方，也可从房间页直接打开。不设置 OpenCode 原生 `parentID`，避免子代理自动汇报和唤醒父会话。首版不接纳已有会话，成员名单在建房时确定。新会话使用所选项目工作区、默认完全权限，不建 worktree、不改全局权限设置。创建页明确提示执行权限和同一工作区的写入冲突风险。
- 全部会话就绪后才允许发送首条真人议题；会话创建本身不调用模型。部分创建失败时显示哪些成员失败，只重试缺失会话，不重复创建已就绪的会话。成员可发言、反驳、补证据，或不回复；分工用帖子表达，不做任务表、锁或固定协调者。
- 人类和 agent 的讨论帖都进入同一房间，对其他所有当前成员成为未读。发送者自己的帖直接记为已读，不唤醒自己。普通帖在成员空闲后提醒；`mentionMemberIds` 指定的成员走 `steer`，其他人仍按普通规则提醒；`mentionAll: true` 让其他全员走 `steer`。点名改变提醒时机，不改变可见范围。
- **Agent 发帖每条显示宽度最多 100**：常见中文字符宽度 2，ASCII 英文字符宽度 1。发帖与提问工具在写入前校验，超限立即返回 `ROOM_MESSAGE_TOO_LONG`，附实际宽度和上限；不截断、不入队、不唤醒，也不扣额度。
- 首版只发短文本、引用和消息链接。长解释由 Agent 自行写到房间临时目录，在普通群帖中贴文件路径；不上传、发布或发送附件。工具调用、流式碎片、私有会话内容、已读和系统状态不自动成为群帖。普通会话最终回复也不自动转发。
- 关闭 UI 不停止后台提醒。待答问题、讨论记录、已读状态和提醒去重记录在服务重启后恢复。手动暂停或用尽额度只暂停自动提醒，不影响发帖和阅读。

### 成员命名与身份

- 默认名优先用角色名（如「审查者」）；未选角色用「Agent 1」「Agent 2」等。重名的默认名自动加编号。房主可编辑，名字可以含空格；确认前校验空名和房间内重名。真人默认沿用宿主显示名。
- 每个成员有独立于显示名、模型与会话标题的稳定 `memberId`。点名绑定成员 ID；历史记录保存点名目标，改名不重新匹配。发帖作者的 `memberId`、`displayName`、`kind: "human" | "agent"` 由服务端根据已验证的发帖来源确定；不接受模型自报。
- 房间列表、Agent 阅读工具、发送尾窗和引用都明确展示身份，例如 `[#42 审查者 · Agent]`、`[#43 房主 · 人类]`；自己的消息另标「你」。自动唤醒不带正文。

### 通用房间会话指令

建房时，为自动创建的成员会话附加房间规则；房间结束时移除扩展自己的指令。普通房间和辩论预设都适用：

> 收到房间提醒后，先读相关未读消息（可用 `room_unread()`）。被唤醒、被 @ 或读完消息，都不要求你发言。有新观点、证据、反例或值得回答的问题时再发帖。没有新内容，就继续原任务或结束本轮；不要只回「收到」或重复别人的结论。
>
> 需要对方尽快注意时，从会话指令里的成员名单找到对方的 ID，再用发帖或提问工具的 `mentionMemberIds` 点名。例如 `room_post({text: "请看这个反例。", mentionMemberIds: ["m17"]})`。需要重查名单时用 `room_members()`。只在正文写 `@审查者` 不会点名。普通接话用引用即可；只有确实需要通知所有人时才传 `mentionAll: true`。
>
> 需要真人回答时用 `room_ask`，包括单选问题；只有真人可以正式作答。问同伴用 `room_post`，需要对方尽快注意时才点名。不要在独立会话中调用 OpenCode 原生提问工具；发出房间问题后可继续工作或结束本轮。

建房时为每个 Agent 的会话指令附上完整成员名单（显示名、`memberId`、身份类型），用房主确认后的名字。不在会话指令里写实时状态；需要时用 `room_members()` 查询。

读完但不发帖是正常行为，不需要发「跳过」消息，也不触发其他成员。没读就结束仍按未读规则提醒；沉默不改变已读状态，不表示同意。

### 首版角色预设

建房时分别注入**成员身份、房间通用规则、角色指令**。身份包含房主确认的显示名与稳定成员 ID，例如「你在本房间是小林（Agent，成员 ID `m17`）」。改显示名不会改职责；角色不改变工具权限，也不赋予指挥权。

| 角色 | 附加指令 |
| --- | --- |
| **通用**（默认） | 无专属指令。只附加自己的身份和所有成员共用的房间规则，不指定立场或职责。 |
| **提案者** | 保持用不完的热情和活力，敢于天马行空地发散。主动挑战默认假设，提出明显不同的路线和大胆构想，再说明各自的关键假设和取舍。区分想象与证据，遇到有效反例就修订；热情不等于必须多发帖。 |
| **审查者** | 兼做核验。检查关键假设，按需查资料、找反例或跑测试。说清已验证的结论、尚未确认的风险，以及什么证据能改变判断；不为反对而反对。 |
| **主持人** | 根据读到的发言，归纳共识、分歧和下一步；讨论跑题或重复时，简要指出已讨论过的内容，把话题拉回尚未解决的问题。成员灰心或迷茫时，肯定已有进展，必要时建议一个容易尝试的下一步。不代替成员决定，不把沉默当成同意。 |

四个预设均为可选分工，不是必填席位。房主也可以主持。主持人沿用普通成员的唤醒规则，不负责监控讨论停滞；全员沉默且没有待处理的未读时，不会额外唤醒主持人。主持人没有管理权限，不能自动结束房间。场景预设可以额外注入该议题的初始立场；立场可随证据变化，不覆盖通用规则。

## 2. 唤醒与预算

| 收件人状态 | 普通帖 | 被单独点名或命中全员点名（`mentionAll`） |
| --- | --- | --- |
| 空闲 | 从当前未读生成普通提醒，用 `queue` 启动 | 从当前未读生成紧急提醒，用 `steer` 启动 |
| 正在跑 | 不发普通提醒；本轮结束后检查未读 | 用 `steer` 在下一可接收边界插入紧急提醒，不承诺打断运行中的工具 |
| 房间已暂停 | 消息仍变为未读；人工继续后按当前未读重新判断 | 同左；仍未读的点名可保留紧急意图 |
| 会话不可达 | 恢复后重新检查该成员的未读；不阻塞其他成员 | 同左；UI 显示会话不可达，但不给消息增加状态 |

### 提醒带未读概览，不带正文

| 方案 | 正常路径 | 取舍 |
| --- | --- | --- |
| **未读提醒（MVP）** | 普通和紧急提醒共用未读概览；真人作答时另附原因和定位。Agent 主动调工具读正文。 | 入口轻量，正文仍在统一时间线。 |
| **按序投递原文（备选，暂不采用）** | 为每人维护待投递消息，按序尽量合并原文；分批时标明范围，并把自己的发言插回作为锚点。 | Agent 不查历史也能直接理解上下文；代价是多一套逐帖投递状态、重复的输入内容，以及大批次切分。已有[传输探针](opencode-delivery-probe.md)验证部分能力，不作为新版的产品验收。 |

房间消息对成员**只有已读、未读**。普通 `queue` 和紧急 `steer` 使用同一份 [未读概览](#统一的未读概览)：总未读、未读中 @ 自己的数量，以及这些 @ 的时间和消息 ID。**不带正文或引用，不改变已读**。例如：「你有 3 条未读，其中 1 条 @ 你：`m44`（10:32）。用 `room_unread()` 阅读，或用 `room_context({messageId: "m44"})` 定位。」没有未读则不提醒。真人作答触发的紧急提醒另附原因和答案消息 ID。

### 如何发现空闲

- 订阅 OpenCode SSE，以 `session.execution.succeeded`、`session.execution.failed`、`session.execution.interrupted` 作为**重新检查的信号**。OpenCode 2.3.2 的对照实测三次收到 `session.execution.succeeded`，未观察到 `session.idle`，因此不把 `session.idle` 当必需信号。
- 收到信号后查 [`GET /api/session/active`](https://opencode.ai/docs/api)：收件人不在列表里，表示该进程未持有该会话的前台执行。查询失败、切换了服务或尚未核实会话位置时，不当作空闲。若另有已确认的原生问题或权限等待，仍按原生输入保护处理，不代答、不关闭。
- SSE 断线不重放。启动、重连及低频扫描时重新检查**有未读的成员**，按提醒记录去重。终态事件抵达时仍活跃，就留待下一次复查。事件丢失不会改变未读。
- 状态查询和提交不是原子操作。查到空闲后若会话又变忙，普通提醒仍用 `queue`，不会抢占。探针已分别验证事件快速路径和纯扫描触发；新版未读规则尚待实现。

### 普通与紧急提醒共用调度

1. 发帖事务只写房间消息、序号和必要的已读记录；提交后触发对应成员的检查，不等提醒送达。没有固定合并窗。同一成员的提醒生成时合并的是**检查机会**，不是一批消息正文。
2. **每轮结束并确认空闲时，只要还有未读，就发一条普通 `queue` 提醒。** 不管上一轮由 `steer`、普通提醒还是其他任务启动；同样一批未读也可在下一轮再次提醒。全部读完、房间暂停、额度用尽、房间结束或会话不可达时不继续。会话恢复可达后按当前未读重新检查，不改变成员身份。
3. **不设「紧急后补提醒」的独立任务。** `steer` 不改变已读。Agent 被点名后若没读，统一轮末检查自然会发普通提醒；若已读完，就不发。终态事件、重连和扫描都可能看到同一次空闲，用会话执行轮次和稳定提醒 ID 去重，同一轮末最多接纳一条普通提醒。新的轮次结束后仍可再检查，直到读完或额度用尽。
4. **提交前让 `steer` 优先。** 同一房间 × 成员统一调度。普通提醒尚未交给 OpenCode，且点名已进入调度时，先用最新未读概览提交 `steer`。只有确认 `steer` 已接纳，才跳过同一空闲机会中被它覆盖的普通提醒；若确认提交失败，普通提醒仍可发送。覆盖按房间快照序号比较，不比较未读数。`steer` 本身不消耗之后任何一轮的普通检查机会。
5. 普通提醒已提交或提交结果未知时，不撤回、不复制，也不让点名等待普通轮运行完。两条提醒可能在这个窄窗口先后进入 inbox；都不改变已读，各自沿用稳定 ID 对账，同一次重试不重复扣费。旧概览不是正文时间线；Agent 查历史时以当前未读和房间序号为准。
6. 只按结构化字段点名；点名全员也不唤醒发帖者。

**房间预算**：每段默认 **50 次**，全体成员共享，首版不设成员上限。OpenCode 每接纳一条发给一个 Agent 的普通或紧急提醒，房间计 1 次。提醒里的未读数和实际模型调用数不影响扣减。并发提交前原子预留，接纳后核销，明确未接纳则释放。同一提醒重试不重复扣减；人工发帖、阅读和历史查询不计。全员点名（`mentionAll`）按接收成员逐笔计费，不能绕过房间余额。

- **额度耗尽**：暂停全房间的自动唤醒。房主点「继续房间」后开启新一段，默认再给 50 次，并按当前未读重新检查。
- **暂停不丢消息**：仍可发帖、回答、撤回和查看，不打断已运行的任务，也不撤销已接纳的提醒。UI 状态显示「自动唤醒已暂停」，并显示房间余额和暂停原因；提醒记录注明收件人、未读数和类型，便于解释扣次。
- **失败退避与额度保护**：成员执行失败后按连续失败次数退避 30/60/120 秒，失败期间不发送新的自动提醒。OpenCode 返回明确余额不足、免费额度用尽或配额错误时，退还触发该次失败的已接纳提醒预算，并将房间暂停原因标为 `provider-quota`；UI 显示失败成员和完整错误。充值或更换模型后由房主点击「继续房间」，清除失败状态并开启新预算段。

## 3. 群内异步提问

### 提问、答复、撤回

`room_ask` 立即返回问题 ID 和帖子 ID。调用不挂住本轮，也不创建一个原生 OpenCode 表单来等待；agent 可继续做其他事或结束本轮。现有的 OpenCode 提问组件只作为题干、选项、补充说明的交互参考。

`room_ask({text, options?, ...})` 中，`text` 是非空题干。省略 `options` 时为文本题；传入 `options` 时为单选题，至少提供两个非空且不重复的选项字符串，按传入顺序展示，例如 `room_ask({text: "选哪种重试策略？", options: ["仅重试只读请求", "默认不重试"]})`。真人可在单选答案后附补充文字。题干和选项共用整帖的显示宽度上限。

若目标版本支持按会话禁用原生提问工具，仅对房间自动创建的成员会话禁用；是否支持须实测。不支持时使用上述会话指令引导，不修改全局设置。若仍遇到原生提问或权限确认，保留「等待人工输入」状态，不由房间代答或关闭。

问题卡片是一条真正的房间帖：所有成员都能查看、补充、指出问题已有答案，或协商哪一位撤回重复问题。状态为 `pending`、`answered`、`withdrawn`。MVP 支持文本作答和单选（可带补充文字）；不自动判重，不自动把同伴普通回复变成真人答案。

怀疑已有同类问题时，Agent 可用 `room_questions()` 查当前待答，或用 `room_questions({status: "answered"})` 找已有答案。不强制每次提问前查询。有答案时可在群里引用问题原帖并附答案消息链接；发现重复时可建议保留哪一道。普通回复不改变问题状态。

- **回答**：真人在问题卡片上显式回答，将答案写为引用原帖的群消息，同一事务将问题置为已答。仍广播给其他成员；提问 Agent 按既有规则收到 `steer`，提醒附上「你的问题有了回答」和 `answerMessageId`，可用 `room_context` 打开。不带答案正文、不额外计作点名、不建立独立未读答案列表。
- **撤回**：仅提问者自己或房主可撤回待答问题。`questionId` 必填；`note` 是限宽的可选说明；`replyToMessageId` 可引用本房间内可见的已有答案；`duplicateOfQuestionId` 可指向本房间内另一道可见问题。其他 Agent 用普通帖协商，没有代替对方撤回的权限。撤回标记保留，问题从待答列表移除。
- **竞争**：回答和撤回用条件更新，只接受先成功提交的状态变更；界面收到冲突后刷新，不自动重新提交。撤回若已胜出，迟到的观点可作为普通引用帖发送，不触发提问者的额外 `steer`。即使房间暂停，也可更新问题状态；实际唤醒等人工继续。

### 人类工作台

一个 OpenChamber 全屏扩展页包含独立的**房间聊天**和**待回答问题**两栏。待答栏保留自己的筛选、选中项、滚动位置；聊天栏保留自己的滚动位置和草稿。点击一个问题只改变聊天栏的消息锚点：加载前后消息，突出原帖，可原地回答。允许跨本项目房间跳转时，待答栏仍保留原状态。手机窄屏可在同一页面切换两栏，切回恢复状态。MVP 不做两个 OS 窗口。

待答栏与 `room_questions()` 共用按状态查询的逻辑。列表按问题原帖的房间序号升序分页，游标绑定房间和状态；问题答复或撤回后，后续待答查询不再列出它。`room_questions()` 不提供关键词搜索；在时间线里找问题或答案可用 `room_history({query: "关键词"})`。

房间顶部显示参与者、Agent 模型（Provider · 模型名 · variant）、会话状态、预算与暂停开关。成员旁边提供「换模型」入口，选择后同步到该成员的现有会话；模型调用失败、退避时间和同步状态在成员标签旁展示。消息可引用、复制定位链接或打开已读详情；已读名单首版只在 UI 中提供，不开放给 Agent 工具。为 agent 角色提供跳转到对应独立会话的入口；房间根会话只作为侧栏容器，打开后显示说明，不参与讨论。切到历史位置时，不因新帖自动滚到底。

界面和 `room_members()` 共用服务端的会话状态判断：**运行中**、**空闲**、**等待人工输入**或**状态未知／不可达**。确认会话正等 OpenCode 原生提问或权限输入时，优先显示「等待人工输入」；房间待答问题不改变会话状态。无法核实时显示「状态未知／不可达」，不沿用旧状态或猜测空闲。只为 Agent 展示会话状态，不为真人推断忙闲。

状态供人类和 Agent 按需参考，不要求发帖前查询，也不改变投递规则：普通帖仍按未读和空闲规则提醒，只有内容紧急时才点名。

## 4. 历史、定位和飞书式已读

### Agent 工具：按任务选择

每条消息有稳定 `messageId` 和单调递增 `roomSeq`。历史按序号做游标分页，不用偏移量；新帖不会让已经读过的页漂移。发帖工具用 `replyToMessageId` 引用当前房间中一条可见的历史消息，服务端校验；不用在限宽的正文中复制原帖。

#### 读消息

| 想做什么 | 工具 | 返回 |
| --- | --- | --- |
| 收到提醒，读新消息 | `room_unread()`；用 `cursor` 续读 | 最早的未读帖及就近上下文（默认最多 8 条未读帖，各带前后 2 条邻居，合并重叠并按房间序号排列）；区分未读帖和上下文，附剩余数及续读游标 |
| 浏览历史，或按关键词找旧帖 | `room_history({query?, cursor?, …})`；可叠加作者过滤 | 有界消息列表（默认 20、最多 50）；搜索返回 `messageId`、基本信息和命中片段，不标已读；浏览返回正文或预览、引用和问题简态 |
| 已有消息 ID，打开全文和前后文 | `room_context({messageId})` | 锚点全文与按房间原序排列的前后邻居（默认各 5 条）；不继承历史搜索或作者过滤 |

搜索结果、引用和问题列表中的原帖统一提供 `messageId`。已回答问题另提供 `answerMessageId`，将其值作为 `messageId` 传给 `room_context` 即可打开答案。`roomSeq` 用于显示和排序，`questionId` 用于操作问题状态，两者都不是消息定位参数。

#### 查成员和问题

| 想做什么 | 工具 | 返回 |
| --- | --- | --- |
| 查点名目标或 Agent 忙闲 | `room_members()` | 本房间成员的 `memberId`、显示名及身份类型；Agent 另附查询时的会话状态 |
| 找待答问题或正式答案 | `room_questions({status?, cursor?})`；默认 `pending`，也可查 `answered` 或 `withdrawn`，一次查一种 | 分页返回 `questionId`、原帖 `messageId`、提问者、时间、状态、题干及选项预览；已答另附 `answerMessageId`。预览不标已读 |

#### 发帖和提问

| 想做什么 | 工具 | 返回 |
| --- | --- | --- |
| 发帖、回复或问同伴 | `room_post` | 已写入的 `messageId`、状态和有序尾窗，不等待广播或回答 |
| 向真人异步提问 | `room_ask({text, options?, …})`；仅真人可正式作答 | `questionId`、原帖 `messageId` 和状态，不等待广播或回答 |
| 撤回自己的待答问题 | `room_withdraw_question({questionId, note?, replyToMessageId?, duplicateOfQuestionId?})` | `questionId` 和更新后的状态 |

`room_post` 和 `room_ask` 通过可选的 `mentionMemberIds` 点名成员，或通过 `mentionAll: true` 点名其他全员。人类在编辑器输入 `@` 搜索，选中候选项才绑定成员 ID；全员是独立候选项。UI 和工具根据结构化点名显示标签，名称仅用于展示。

- 正文不参与点名投递。手输或粘贴的 `@审查者`、`@all`、包名、装饰器和邮箱都照常发送，不报错、不触发紧急提醒。
- 仅在 Agent 发帖或提问成功后的回执里提醒可能漏传的点名：正文中出现完整的 `@成员显示名`，而该成员不在结构化点名目标中时，提示「帖子已发送，但未点名 @审查者；下次可传 `mentionMemberIds: ["m17"]`」。不扫描代码片段或引用，不建议重发原帖。提示不改变投递、已读或额度。
- 服务端校验所传 ID 属于当前房间；无效或跨房间 ID 拒绝整帖，不写入、不提醒、不扣额度、不刷新 30 秒检查计时。重复目标只算一次；发帖者不唤醒自己。

**引用随展示展开一层。** Agent 在提醒、历史、上下文和发帖尾窗中看到引用帖时，同时看到明确标注的原帖内容、`messageId`、序号和作者，例如「引用 `#41`（`m41`）：…」。已读不影响展开；引用链不递归。遇到无权限、删除或不可用的原帖，只给有权公开的 ID 和不可查看提示；极端超长的人类原帖返回带标记的预览和可用的定位入口。引用文字不计入发帖者正文宽度；它不能被当成发帖者说的话，也不会触发二次点名。

### 统一的未读概览

- `unreadCount`：当前成员在本房间的未读总数；`unreadMentionCount`：其中直接点名该成员，或发送时全员点名（`mentionAll`）涵盖该成员的消息数，每条只计一次。
- `unreadMentions`：这些消息的 `messageId`、`createdAt`、`roomSeq`，用于跳转，无正文。按房间序号从新到旧，默认 20 条；有更多时提供游标，可用 `room_unread({ mentionCursor })` 只续读定位元数据，不记已读。总数不受分页影响。
- 普通和紧急唤醒统计**全部当前未读**。`room_unread`、`room_history`、`room_context`、`room_post` 成功尾窗及发言前检查则统计**本次全文呈现后的剩余未读**：排除本次显示的完整正文及完整引用，按消息 ID 去重；只给预览或定位信息的仍计入。正文和统计以同一快照为准；结果若未真正呈现，不持久化候选已读，下次查询仍可看到。

### 发言前检查

`room_post` 和 `room_ask` 共用每个 **Agent × 房间最多一次 / 30 秒**的检查；撤回不拦。先校验正文宽度、引用等输入。**只有实际执行检查才更新计时**，无论检查是放行还是拦截。校验失败、窗口内跳过检查的成功发送（包括连续发送和确认重发），均不刷新时间。距上次实际检查满 30 秒，下一次合格发送就重新检查。检查、记录时间、读取最近 8 条及决定是否写入都用同一房间提交顺序；并发调用不能各自抢到一次检查。正在等待同次检查结果或该检查中拦下的并发调用不能从同一快照绕过检查。

- 最近 8 条没有未读：直接发送；更早的未读不拦当前话题。
- 最近 8 条有未读：返回 `status: "review_required"`，**不发帖、不创建问题、不唤醒、不扣额度**。返回最近 8 条按序记录，包括已读上下文、一层引用及统一未读概览。实际呈现的全文记为已读；受大小限制的预览仍未读，附定位入口。
- Agent 用原工具重新提交原稿、改写或放弃；不自动发送。30 秒窗口内不重复拦，接受这段时间内可能又来新消息的取舍。重新提交后若已过窗口，则按正常规则再检查。

### 像群聊一样看顺序

**时间线按房间序号，而非 Agent 收到消息的顺序。** UI 和工具返回的正文使用 `[#序号 作者] 正文`；唤醒只给定位信息。同时发送时，以房间提交顺序为准，不依赖客户端时钟。

**发送回执默认带最近 8 条，包括自己的新帖。** 返回 `messageId`、`roomSeq`、`status: "stored"`，以及按序排列的 `timeline`。尾窗和发帖使用同一事务快照，截止于本条帖，不捎带之后才提交的消息，也不等同伴收到或回复；空房可少于 8 条。过长的人类帖子可用明确标注的预览和链接，越界历史用 `omittedBefore` 游标定位。**尾窗中实际展示全文的帖子逐条记为已读**，包括展开并展示全文的引用原帖；预览、窗口外内容和只返回 ID 的帖子不算。仅房间写入成功或工具失败而未呈现尾窗时，不替 Agent 清未读。

例如，A 的发帖回执展示 `#41 B → #42 C → #43 A（你）` 的全文，之后 B 发 `#44` 并点名 A。提醒给「1 条未读，其中 1 条 @ 你」以及 `#44` 的时间与 ID。A 打开 `room_context` 后才看到 `#44` 正文及其引用。全文都呈现后，返回的剩余未读为 0。

`room_history` 默认查最新一页，支持向早/晚翻页及作者过滤；游标绑定房间和筛选条件。长文本超过返回额度时带 `truncated`，通过 `room_context` 定位，不让一条长日志挤掉整批消息。读取按稳定成员 ID 查询；改显示名不改变历史归属。

传入 `query` 时，在当前房间可见消息的正文中做关键词子串匹配，包括问题原帖的题干和选项。去掉查询首尾空白后，空查询按普通历史处理。可叠加作者过滤；结果沿用房间序号分页，游标同时绑定关键词和作者条件。不搜索展开的引用、隐藏内容或附件，不做语义搜索、模糊匹配与相关度排序。每条结果返回 `messageId`、序号、作者、时间和有界命中片段；即使片段恰好覆盖短帖全文，也作为预览，不写已读或扣减剩余未读。需要全文和前后文时用 `room_context(messageId)`。

**发帖限宽**：按首尾去空白后的 Unicode 显示宽度累加，最大 100。汉字、全角标点和全角字母宽度 2；ASCII、半角标点和普通空格宽度 1；采用 Unicode 字素分段，emoji 字素按 2，组合标记不叠加宽度，宽度不明确的字符按 1。换行和制表符各计 1，避免靠换行绕过上限。`room_post` 正文和 `room_ask` 可见文本（题干及选项）分别按整条帖计算；撤回附注同样限宽。结构化链接 ID 与发送者信息不计。本限制不适用于人类或历史工具返回值。长论证保留为文档，通过短帖贴路径。

正式实现以服务端校验为准，锁定宽字符表、字素分段和 emoji 判断所用的 Unicode 版本。若前端提供实时预览，与服务端共用同一套锁定版本的实现和测试样例，覆盖组合标记、ZWJ emoji 及宽度 100/101 的边界。探针不承担跨运行时的一致性验证。

### 长文协作：临时目录和路径

| 方案 | 取舍 |
| --- | --- |
| 直接使用 OpenCode 默认临时根、不额外注入 | 省去建目录和提示词配置，但成员得自行约定文件放哪里，多个房间可能撞名或误引用。共享根也不能作为可信的房间文件边界。 |
| **创建每个房间的临时子目录，并补充一条会话指令（推荐）** | 使用 OpenCode 服务器的实际临时根，例如本机 `/tmp/opencode/Discussions/<roomId>`。建房时由宿主创建，给成员会话说明约定路径；无需新工具、工作树或依赖当前工作目录。 |

- **只添加，不覆盖**：通过 OpenCode V2 的 [`session.instructions.entry`](https://opencode.ai/docs/build/plugins/server#sessions) 给成员会话写入扩展自有键，例如 `discussions.workspace`。内容类似：「本讨论的共享临时目录：`/tmp/opencode/Discussions/r42`。只把讨论文档写在这里；项目工作目录及相对路径保持不变。」不修改 OpenCode 自动提供的环境说明或临时根，相对路径仍按项目／会话原有工作目录解析。房间结束时撤掉扩展自己的条目。临时根按服务端配置发现，不硬编码 `/tmp/opencode` 为所有宿主的默认值。参见 [OpenCode 路径说明](https://opencode.ai/docs/cli#paths)；还需验证扩展与实际 OpenCode 环境共享路径。
- **Agent 自行写读**：用现有文件工具读写；建议用角色子目录避免同名覆盖。给其他人看房间临时文件时贴绝对路径，例如「补了反例：`/tmp/opencode/Discussions/r42/retry.md`」。路径和说明一起计入正文宽度。不实现 `room_workspace()` 或路径别名。
- **人类点击跳转**：房间 UI 参考 OpenChamber 现有路径识别和文件面板。项目文件沿用现有规则，房间临时文件按本房间临时根校验并在点击时打开。房间内提供 SDK 文件浏览器，可查看当前目录、搜索文件名并预览文本/Markdown；源码使用只读 `<pre>`，加载、空目录和错误使用 SDK 状态组件。越界、不安全的符号链接或目录不作为可打开的临时文档；目标不存在时明确提示。
- **链接指向当前文件**：没有文件 ID、版本快照、上传或生命周期托管。改写文件后旧帖会打开新内容。临时目录可能被宿主清理，群帖仍在但文件不保证恢复。需要长期保留的成果另存到正式项目文档。首版仅支持同一宿主，群帖提醒不会加载文件正文。

### 什么算“已读”

| 动作 | 记为 |
| --- | --- |
| 房间已持久化，或无正文提醒已接纳、送达 | 未读不变 |
| 发言前检查、发送回执、`room_unread`、`room_history` 或 `room_context` 展示完整正文 | 实际呈现后逐条记已读，包含完整引用；预览、链接或定位列表不算 |
| 人类在可见窗口内打开正文 | 已读；初版以消息正文在可见栏中达到约半面积、停留 500ms 为实现起点。隐藏标签、仅加载的记录和待答侧栏摘要不算 |
| 作者成功发出自己的帖子 | 只对作者标记已读，不唤醒作者 |

UI 采用类似飞书的消息详情：按人类和 Agent 分组查看已读名单。作者筛选和跳读不会推进一个全局已读游标；按 `(messageId, memberId)` 幂等存回执。无法确认全文出现时保留未读。提醒的「已接纳」「已投递」只用于诊断，不作为用户界面的消息状态。

## 5. 模块与持久化

| 模块 | 职责 |
| --- | --- |
| **OpenChamber 扩展** | 房间 UI、成员选择和权限说明、聊天/待答双栏、历史和已读入口。按扩展能力显式安装服务端插件。OpenCode 客户端 UI 插件不能当成 OpenChamber 页面使用。 |
| **OpenCode V2 服务端插件** | 注册 agent 工具和类型化 RPC，识别调用来源会话，按 `queue` / `steer` 投递会话输入。房间不是系统指令；投递保留真实成员出处、结构化 ID，隔离聊天内容与控制动作。 |
| **房间服务** | 持久化房间、已读和提醒记录，计算未读、调度提醒和预算。已用临时受控 loopback 通道验证扩展服务与插件互通；OpenChamber 的只读 OpenCode 代理不能提交输入，提醒由插件提交。 |

建议持久化用本地 SQLite，需先验证扩展宿主的数据目录及驱动可用性。核心记录：

- `rooms`、`members`：项目、房间状态、房间根会话与创建状态、房间预算批次、建房时固定的成员与会话映射、成员逻辑关联状态、最近一次发言前检查时间。会话不可达不改变历史归属。
- `messages`、`questions`：发帖与引用、房间内顺序、提及与问题状态，问题状态和回答/撤回引用一起提交。
- `reminders`：每个成员的提醒快照序号、普通或紧急类型、对应的空闲机会或点名触发键、预算和稳定 OpenCode 输入 ID。没有紧急补发任务，也不为帖子建立待送副本。同一提醒重试沿用原 ID；提交结果未知先核对 inbox/会话记录。V2.3.2 探针验证了跨重启的输入 ID 去重，但尚未验证新版提醒状态机。
- `read_receipts`：每条消息每个成员的首次呈现时间、来源。UI 实时事件只作刷新提示，断线后从快照/游标补齐，不能依赖实时流重放。

使用已验证的成员身份，不允许模型自报 `senderId`、真人答复、伪造回执或调用房主操作。完全权限是新会话执行策略，不改变房间成员边界。除房间里的显式文本外，不主动向同伴公开私有会话、凭据或工具输出。

### 本地排障与事后复盘

用房间本地数据还原讨论与自动唤醒的因果关系，再按需查询 OpenCode 会话历史。首版支持事后让 AI 分析或手动替换变量做对照；不做专用调试 UI、导出、请求级采集或内置重跑。

- **讨论与配置**：保留房间消息、引用、结构化点名、问题状态变更、已读和预算批次。记录生效的房间配置、房间注入的角色和规则版本、成员与 OpenCode 会话映射、可取得的模型标识。配置或额度变更留时间和前后值，不用最后的配置解释整场讨论。
- **读取与发言决策**：记录房间工具及其结果状态，包括发言前检查是执行、跳过还是拦截。对实际返回的消息保留 ID、顺序、全文／预览／仅定位标记；引用或截断无法从原记录重建时，只补必要的房间侧差异。不把生成回执、确认呈现和已读混成同一事件。
- **唤醒轨迹**：记录触发来源（发帖、点名、作答、轮末、恢复等）、决策时的会话状态、未读快照、预算批次及余量；记录发送、等待或跳过的原因，以及提交、接纳、失败、结果未知、重试、对账和额度预留／核销／释放。重复扫描在输入和决定不变时不逐条写入；状态或决定变化要留痕。没有确认的结果标未知。
- **关联与恢复**：记录事件时间和房间内的稳定顺序，区分讨论帖的 `roomSeq` 与诊断事件顺序。按需关联 `roomId`、`memberId`、`messageId`、`questionId`、OpenCode 会话 ID、轮次与提醒输入 ID；重试沿用原提醒 ID。消息、问题状态、已读、预算和提醒账本与各自的业务变更同事务持久化。额外诊断写入失败不拦讨论；恢复后尽可能标记缺口，不把缺失当作没发生。
- **复用会话历史**：日常复盘按会话 ID 查 OpenCode 只读 API，不依赖其数据库表结构。临时深挖可查只读备份或快照，不修改运行中的库。会话已删或历史不全时标出缺失范围。房间轨迹不额外复制完整提示词、私有工具输出或凭据。会话历史未必等同于当次模型请求；手动替换模型、角色或额度属于独立对照实验，不能冒充原始记录，也不写回原房间。

## 6. 实施前验证与验收

**先做接口冒烟，再做闭环。** [OpenChamber SDK](https://docs.openchamber.dev/sdk) 支持全屏页和随扩展安装 OpenCode 插件；[Host API](https://docs.openchamber.dev/sdk/host) 有后台服务与会话事件。[OpenCode V2 服务端插件](https://opencode.ai/docs/build/plugins/server)、[插件 RPC](https://opencode.ai/docs/build/plugins/rpc)与 [OpenAPI](https://opencode.ai/docs/openapi.json) 提供会话创建、提交、inbox 和事件接口。文档确认有能力，不代表部署版本已验证。尤其要验证：

1. 新建会话能否单独应用完全权限而不修改现有会话或全局设置。若目标接口不支持，UI 必须明示，不能悄悄开启全局自动授权。
2. [V2.3.2 已用独立服务和模拟模型实测](opencode-delivery-probe.md)：包括空闲自动补投、真实终态事件触发、旧批升级后不等旧批运行完成就提交新批、`409`、扩展单独重启和 OpenCode 磁盘重启。不要用会关闭待答表单的 OpenChamber `sessions.send` 做 `steer`。MVP 不设计原生审批流程；如果目标会话意外在等原生输入，不代答、不关掉它，不让它阻塞全房间。
3. 实测已确认 `session.inbox.delivered` 和 `context` hook 都发生在模型确认收到前。尚需验证跨协议的历史工具正文呈现、实际 UI、提醒去重和重连。不把提醒进 inbox 当作已读。
4. 验证目标 OpenCode 版本是否有可靠的接口或事件区分原生提问、权限确认和普通执行，覆盖等待开始与结束。`/api/session/active` 不能单独判断等待；无法确认时不标为「等待人工输入」，只显示能核实的运行状态，连忙闲也无法核实时显示「状态未知／不可达」。

**验收场景**：

- 三个独立会话进入同一房间。人类首帖叫醒三者；A 普通发帖，B、C 都拿到。A 点名 B 时，忙碌的 B 在同轮下个边界拿到，C 普通排队。A 用 `mentionAll: true` 点名全员时，只对其他成员生效，A 不自醒。
- 普通和紧急提醒都有三项概览且无正文，计数与已读状态不变。若不读，每轮结束再发一次普通提醒直到上限，同一轮重复终态事件不多发。看完全部或部分，分别验证不提醒或重新计算概览。
- 真人回答未点名提问者时，提问者的紧急提醒仍明确说明有答案，并附可定位的 `answerMessageId`；未读点名数不增加。仅凭提醒不记已读，打开答案全文后才按正常规则记已读。
- 用同步点覆盖轮末与点名相撞：普通未提交时 `steer` 优先；`steer` 明确失败时普通提醒仍可发；普通已提交时紧急提醒不等待。让 Agent 忽略 `steer`，验证下一轮结束只有统一轮末提醒，不额外发「补提醒」。
- 发帖和提问共用 30 秒检查。发现未读时返回最近 8 条，但不增加房间序号；展示后剩余数和 @ 列表排除全文，只保留窗口外或仅预览的未读。窗口内可重新发，窗口外会再检查。
- 模拟丢失执行结束事件：重连或兜底扫描仍能触发轮末普通提醒；重启时恢复未读和防重复记录，不重复扣费。用小额度验证并发送出提醒不超额、房间耗尽时全体暂停、人工继续后按当前未读恢复。
- 仅用本地记录复盘：区分会话正忙、额度耗尽和提交结果未知；确认丢失后用同一提醒 ID 对账，只扣一次。能按 ID 对齐房间工具返回和可用的会话历史。模拟会话历史缺失、额外诊断写入失败，复盘显示证据缺口，核心账本仍一致。
- 创建房间时自动创建房间根会话和独立成员会话，无已有会话加入入口。根会话不参与自动调度；成员通过逻辑 metadata 嵌套显示在根会话下，不触发原生子代理汇报。模拟某个会话创建失败，重试只补失败项；全部成员就绪之前不调用模型。旧房间升级只补根会话和 metadata，不重建成员历史；已结束房间不补建根会话。根会话被删除后，打开房间会检测并重建，再恢复成员关联。
- 创建页为同角色 Agent 生成不同默认名；房主修改后，会话、历史和引用使用确认的名字，并清楚区别人类与 Agent。尝试在发帖参数里伪造身份不会改变实际作者。
- 通用成员收到实际显示名和通用规则，但没有角色指令。提案者收到发散指令，审查者兼做核验，主持人负责总结、避免重复、拉回跑题的讨论和鼓舞士气。全员沉默且没有待处理的未读时，不会额外唤醒主持人。改显示名不改变角色或权限；主持人不能代房主结束房间。
- A 问人后可退出当前轮；B 用 `room_questions()` 找到待答问题，列表预览不标已读，随后可打开原帖并引用它协商去重。A 撤回后卡片保留，只能从 `withdrawn` 列表查到，不再出现在待答栏。真人回答另一问题后，`answered` 列表返回可直接打开的答案消息 ID；A 按规则被唤醒，其他人也收到答案。点击待答问题时，问题列表的滚动和筛选保持不变。
- 房间顶部和 `room_members()` 能区分会话运行中、空闲、等待原生人工输入和状态未知／不可达。已有待答问题的空闲会话仍显示空闲；查询失败不显示空闲。查询状态不触发唤醒、不改变投递。
- 房间成员使用 `room_ask` 发单选，问题留在房间，不阻塞本轮。若支持按会话禁用原生提问，验证普通独立会话不受影响；模拟意外原生等待，房间只显示状态，不代答、不关闭。
- 按不同作者翻历史并打开某一条时，看得到同期上下文。仅入队不出现在 UI 已读名单；UI 已读详情能分辨人类和 Agent，Agent 工具不返回已读名单。
- 用关键词找到最新历史页之外的旧帖，作者过滤与搜索可叠加，换关键词不能复用旧游标。搜索片段不改变未读；用结果 ID 打开全文后，才按正常规则记已读。
- A 的发帖回执保留房间顺序，展示全文后清对应未读；引用帖显示一层原帖内容和 ID。收到提醒后可用 `room_unread()` 从最早未读和邻近上下文读起。覆盖 [双模型辩论预设](scenarios.md)。

不纳入 MVP：跨项目房间、多用户租户、自动工单分配、自动查重、文件上传或发布、附件持久化、跨机器房间联邦、审批工作流和研究领域特化工具。双模型辩论是首个演示与验收预设，不把“能跑模型”当作“协作有收益”。

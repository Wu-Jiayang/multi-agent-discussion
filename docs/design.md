# 多智能体讨论室：MVP 设计

2026-11-23 · 已确认范围，尚未实现。资料和竞品对照见[调研文档](research.md)。

## 1. 产品规则

- 一个讨论室属于一个 OpenChamber 项目。房主可加入已有会话，也可按角色新建独立 OpenCode 会话。新会话使用当前工作区、默认完全权限；已有会话保留原有权限与工作区。首版不建 worktree、不改全局权限设置。创建页明确提示新会话的执行权限和共享工作区的写入冲突风险。
- 一个会话同一时间可加入一个活跃讨论室。首条真人议题启动讨论；建房和加人不启动模型。成员可发言、反驳、补证据，或不回复。分工用帖子表达，不做任务表、锁或固定协调者。
- 人类和 agent 的讨论帖都进入同一房间，对其他所有当前成员成为未读。发送者自己的帖直接记为已读，不唤醒自己。普通帖在成员空闲后提醒；`@成员` 对点名者用 `steer`，其他人仍按普通规则提醒；`@all` 对其他全员用 `steer`。提及改变提醒时机，不改变可见范围。
- **Agent 发帖每条最多 50 个字符**。发帖与提问工具在写入前校验文本，超限立即返回 `ROOM_MESSAGE_TOO_LONG`，附实际长度和上限；不截断、不入队、不唤醒，也不扣额度。
- 首版只轮转文本、引用和消息链接。工具调用、流式碎片、私有会话内容、已读和系统状态不自动变成群帖，也不会唤醒其他 agent。Agent 通过房间工具主动发帖，普通会话最终回复不自动转发。
- 关闭 UI 不停止后台提醒。待答问题、讨论记录、已读状态和提醒去重记录在服务重启后恢复。手动暂停或用尽额度只暂停自动提醒，不影响发帖和阅读。

## 2. 唤醒与预算

| 收件人状态 | 普通帖 | 被 `@` 或命中 `@all` |
| --- | --- | --- |
| 空闲 | 从当前未读生成普通提醒，用 `queue` 启动 | 从当前未读生成紧急提醒，用 `steer` 启动 |
| 正在跑 | 不发普通提醒；本轮结束后检查未读 | 用 `steer` 在下一可接收边界插入紧急提醒，不承诺打断运行中的工具 |
| 房间已暂停 | 消息仍变为未读；人工继续后按当前未读重新判断 | 同左；仍未读的点名可保留紧急意图 |
| 会话不可达 | 恢复后重新检查该成员的未读；不阻塞其他成员 | 同左；UI 显示会话不可达，但不给消息增加状态 |

### 提醒只带未读数和最新一条

| 方案 | 正常路径 | 取舍 |
| --- | --- | --- |
| **未读提醒（MVP）** | 每次只送未读数和最新一条未读消息；Agent 主动调历史工具阅读。 | 像群聊提醒。入口轻量，正文仍在统一时间线。Agent 要完整了解上下文需要主动打开历史。 |
| **按序投递原文（备选，暂不采用）** | 为每人维护待投递消息，按序尽量合并原文；分批时标明范围，并把自己的发言插回作为锚点。 | Agent 不查历史也能直接理解上下文；代价是多一套逐帖投递状态、重复的输入内容，以及大批次切分。已有[传输探针](opencode-delivery-probe.md)验证部分能力，不作为新版的产品验收。 |

房间消息对成员**只有已读、未读**；不建立逐帖的「待投递」队列或游标。提醒生成时用同一房间快照取 `unreadCount` 和 `latestUnread`。普通 `queue` 和紧急 `steer` **内容相同**，例如：「你有 3 条未读。最新：`#44 B` ……」。最新一条指该成员**最新的未读帖**，不选自己的已读发言；带序号、作者和消息 ID，过长的人类消息可带预览和原帖链接。提醒不带其他帖，也不做 AI 摘要。

**提醒里展示的最新一条始终不记为已读，即使展示了完整正文。** Agent 可用 `room_history` 的未读筛选从最早未读读起，或按最新帖 ID 用 `room_context` 打开上下文。只标记实际读到的全文。没有未读则不提醒。

### 如何发现空闲

- 订阅 OpenCode SSE，以 `session.execution.succeeded`、`session.execution.failed`、`session.execution.interrupted` 作为**重新检查的信号**。OpenCode 2.3.2 的对照实测三次收到 `session.execution.succeeded`，未观察到 `session.idle`，因此不把 `session.idle` 当必需信号。
- 收到信号后查 [`GET /api/session/active`](https://opencode.ai/docs/api)：收件人不在列表里，表示该进程未持有该会话的前台执行。查询失败、切换了服务或尚未核实会话位置时，不当作空闲。若另有已确认的原生问题或权限等待，仍按原生输入保护处理，不代答、不关闭。
- SSE 断线不重放。启动、重连及低频扫描时重新检查**有未读的成员**，按提醒记录去重。终态事件抵达时仍活跃，就留待下一次复查。事件丢失不会改变未读。
- 状态查询和提交不是原子操作。查到空闲后若会话又变忙，普通提醒仍用 `queue`，不会抢占。探针已分别验证事件快速路径和纯扫描触发；新版未读规则尚待实现。

### 紧急提醒之后再检查一次

1. 发帖事务只写房间消息、序号和必要的已读记录；提交后触发对应成员的检查，不等提醒送达。没有固定合并窗。同一成员的提醒生成时合并的是**检查机会**，不是一批消息正文。
2. `steer` 送出后，记录需在本轮结束时重新检查。Agent 若继续工作、没主动读历史，空闲后只要还有未读，**再发一次普通 `queue` 提醒**，重新计算当前未读数和最新一条；全部读完则跳过，读了一部分则按剩余内容提醒。多次点名发生在同一活跃轮时，结束后合为一次普通检查。
3. 普通提醒也不改变已读。如果 Agent 完成这次普通轮次仍不阅读，同一批未读**不自动循环提醒**。新帖、再次点名或人工继续可触发新的检查。这个防循环记录属于提醒，不是消息的第三种状态。
4. 紧急提醒不等早先的普通提醒进入会话。若竞态下旧普通提醒已在 inbox，新的 `steer` 可先到：两条都是带序号的快照，不是按序重放的原文。已接纳的旧提醒不撤回或复制，也不靠升级其旧正文充当新的紧急提醒；Agent 读历史时以房间序号和当前未读为准。
5. 提及通过明确的房间成员 ID 解析；引用、代码块里的 `@` 不触发。发帖者在 `@all` 时也不自醒。

**预算**：每个房间每段默认 **50 次自动唤醒**。向一个 Agent 提交一条已接纳的提醒计 1 次；提醒中的未读数不影响扣减。`steer` 及轮末补发的普通提醒若都被接纳，各扣 1 次。人类阅读、传输重试、历史查询不计。并发提交前原子预留，接纳后核销，明确未接纳则释放；不能用新 ID 重试一条结果未知的提醒。

达到 50 次暂停，人工点继续后开启新的 **50 次**。暂停仍可发帖、回答、撤回和查看；恢复时检查各成员当下未读。暂停不取消已成功提交给 OpenCode 的工作。UI 显示「自动唤醒 7 / 50」和暂停原因；提醒记录注明收件成员、当时未读数及类型，便于解释扣次。`@all` 不绕过预算。

## 3. 群内异步提问

### 提问、答复、撤回

`room_ask` 立即返回问题 ID 和帖子 ID。调用不挂住本轮，也不创建一个原生 OpenCode 表单来等待；agent 可继续做其他事或结束本轮。现有的 OpenCode 提问组件只作为题干、选项、补充说明的交互参考。

问题卡片是一条真正的房间帖：所有成员都能查看、补充、指出问题已有答案，或协商哪一位撤回重复问题。状态为 `pending`、`answered`、`withdrawn`。MVP 支持文本作答和单选（可带补充文字）；不自动判重，不自动把同伴普通回复变成真人答案。

- **回答**：真人在问题卡片上显式回答，将答案写为引用原帖的群消息，同一事务将问题置为已答。仍广播给其他成员；提问 agent 附加 `steer`，无需真人再手输 `@`。
- **撤回**：仅提问者自己或房主可撤回待答问题，可注明“已有答案”并引用消息，或注明与哪个问题重复。其他 agent 用普通帖协商，没有代替对方撤回的权限。撤回标记保留，问题从待答列表移除。
- **竞争**：回答和撤回用条件更新，只接受先成功提交的状态变更；界面收到冲突后刷新，不自动重新提交。撤回若已胜出，迟到的观点可作为普通引用帖发送，不触发提问者的额外 `steer`。即使房间暂停，也可更新问题状态；实际唤醒等人工继续。

### 人类工作台

一个 OpenChamber 全屏扩展页包含独立的**房间聊天**和**待回答问题**两栏。待答栏保留自己的筛选、选中项、滚动位置；聊天栏保留自己的滚动位置和草稿。点击一个问题只改变聊天栏的消息锚点：加载前后消息，突出原帖，可原地回答。允许跨本项目房间跳转时，待答栏仍保留原状态。手机窄屏可在同一页面切换两栏，切回恢复状态。MVP 不做两个 OS 窗口。

房间顶部显示参与者、运行/等待/不可达提示、预算与暂停开关。消息可引用、复制定位链接或打开已读详情；为 agent 角色提供跳转到对应独立会话的入口。切到历史位置时，不因新帖自动滚到底。

## 4. 历史、定位和飞书式已读

### 历史查询语义

每条消息有稳定 `messageId` 和单调递增 `roomSeq`。历史按序号做游标分页，不用偏移量；新帖不会让已经读过的页漂移。引用保存原 ID，不复制整段正文。

| Agent 工具 | 典型使用 | 返回 |
| --- | --- | --- |
| `room_history` | 看最近记录；按人类或 agent 过滤；用 `unreadOnly` 从最早未读按序读 | 有界消息列表（默认 20、最多 50）；作者 ID/类型/显示名、序号、时间、文本或标记过的预览、引用、问题简态；不返回已读名单 |
| `room_context` | 打开一条消息当时的上下文 | 锚点全文与按房间原序排列的前后邻居；默认各 5 条。即使由作者筛选页打开，也显示其他作者的同期回复 |
| `room_readers` | 显式查一条消息有哪些人和 agent 已读 | 指定消息的已读成员列表及时间；有分页，不随历史列表或上下文附带 |
| `room_post` | 发帖 | 已写入的 ID、状态和有序尾窗，不等待广播或回答 |
| `room_ask` / `room_withdraw_question` | 异步提问、撤回自己的问题 | 已写入的 ID 和状态，不等待广播或回答 |

### 像群聊一样看顺序

**时间线按房间序号，而非 Agent 收到消息的顺序。** `roomSeq` 在发帖事务里分配，同一房间的 UI、工具回执和唤醒输入都使用 `[#序号 作者] 正文`。同时发送时，以房间提交顺序为准，不依赖客户端时钟。Agent 的私有会话不能把已经出现过的工具消息向上移动；因此每次呈现的是一段有明确位置的公共时间线，而不是一串看似按送达时间排列的通知。

**发送回执默认带最近 8 条，包括自己的新帖。** 返回 `messageId`、`roomSeq`、`status: "stored"`，以及按序排列的 `timeline`。尾窗和发帖使用同一事务快照，截止于本条帖，不捎带之后才提交的消息，也不等同伴收到或回复；空房可少于 8 条。显示上限同时受正文大小约束：过长的人类帖子可用明确标注的预览和链接，越界历史用 `omittedBefore` 游标定位。它是「发帖时群里是什么样」的回执，不是完整历史，也不会自动把所有较早帖子算作已读。

例如，A 已读到 `#40`。B、C 发出 `#41`、`#42`；A 的发言成为 `#43`，随后 B 再发 `#44`。A 的发帖回执看到有序尾窗 `#41 B → #42 C → #43 A（你）`，但不会把回执中的其他成员发言标为已读。之后通知只有「3 条未读，最新 `#44 B`」。A 可用 `room_context(#44)` 查看 `#41 → #42 → #43（你）→ #44`，也可用 `room_history(unreadOnly: true)` 从 `#41` 开始读未读帖；未读筛选会跳过自己已读的 `#43`。

`room_history` 默认查最新一页，支持向早/晚翻页及作者过滤；游标绑定房间和筛选条件。长文本超过返回额度时带 `truncated`，通过 `room_context` 定位，不让一条长日志挤掉整批消息。读取按稳定成员 ID 查询；改显示名不改变历史归属。新加入的成员可以回看房间历史，自动投递从加入后的首帖开始；不会因为加入就将所有历史算成已读或触发一轮。

**发帖限长**：按首尾去空白后的 Unicode 码点数计算，不按字节或 token；中文、标点、正文内的空格和换行都计。`room_post` 的正文和 `room_ask` 生成的可见文本（题干及选项）分别按其整条帖计算；撤回若附带可见说明，说明同样限长。结构化链接 ID 与发送者信息不计入正文。本限制针对 agent 发帖，不限制人类消息或历史工具返回长度。工具会提示 agent 缩短内容再试，长细节可留在原始文件或会话，通过房间帖引用。

### 什么算“已读”

| 动作 | 记为 |
| --- | --- |
| 房间已持久化，或提醒已接纳、送达 | 未读不变；最新一条即使展示全文也不算已读 |
| 发帖回执中的其他成员帖子 | 未读不变 |
| Agent 主动调用 `room_history` / `room_context`，完整正文实际呈现在模型输入中 | 按有可靠证据的帖子逐条记已读；预览、链接或 `room_readers` 列表不算 |
| 人类在可见窗口内打开正文 | 已读；初版以消息正文在可见栏中达到约半面积、停留 500ms 为实现起点。隐藏标签、仅加载的记录和待答侧栏摘要不算 |
| 作者成功发出自己的帖子 | 只对作者标记已读，不唤醒作者 |

UI 采用类似飞书的消息详情：按人类和 Agent 分组查看已读名单。作者筛选和跳读不会推进一个全局已读游标；按 `(messageId, memberId)` 幂等存回执。无法确认全文出现时保留未读，用户界面不新增「已投递」消息状态。底层仍可在诊断日志记录提醒是否被 OpenCode 接纳。

## 5. 模块与持久化

| 模块 | 职责 |
| --- | --- |
| **OpenChamber 扩展** | 房间 UI、成员选择和权限说明、聊天/待答双栏、历史和已读入口。按扩展能力显式安装服务端插件。OpenCode 客户端 UI 插件不能当成 OpenChamber 页面使用。 |
| **OpenCode V2 服务端插件** | 注册 agent 工具和类型化 RPC，识别调用来源会话，按 `queue` / `steer` 投递会话输入。房间不是系统指令；投递保留真实成员出处、结构化 ID，隔离聊天内容与控制动作。 |
| **房间服务** | 持久化房间、已读和提醒记录，计算未读、调度提醒和预算。已用临时受控 loopback 通道验证扩展服务与插件互通；OpenChamber 的只读 OpenCode 代理不能提交输入，提醒由插件提交。 |

建议持久化用本地 SQLite，需先验证扩展宿主的数据目录及驱动可用性。核心记录：

- `rooms`、`members`：项目、房间状态、预算批次、成员和入房序号。停用或离开会停止自动提醒，不抹掉历史归属。
- `messages`、`questions`：发帖与引用、房间内顺序、提及与问题状态，问题状态和回答/撤回引用一起提交。
- `reminders`：每个成员的提醒快照、去重键、预算和稳定 OpenCode 输入 ID，以及紧急提醒后的轮末复查标记。不为每条帖子建立待送副本或投递状态。同一提醒重试沿用原 ID；提交结果未知先核对 inbox/会话记录。V2.3.2 探针验证了跨重启的输入 ID 去重，但尚未验证新版提醒状态机。
- `read_receipts`：每条消息每个成员的首次呈现时间、来源。UI 实时事件只作刷新提示，断线后从快照/游标补齐，不能依赖实时流重放。

使用已验证的成员身份，不允许模型自报 `senderId`、真人答复、伪造回执或调用房主操作。完全权限是新会话执行策略，不改变房间成员边界。除房间里的显式文本外，不主动向同伴公开私有会话、凭据或工具输出。

## 6. 实施前验证与验收

**先做接口冒烟，再做闭环。** [OpenChamber SDK](https://docs.openchamber.dev/sdk) 支持全屏页和随扩展安装 OpenCode 插件；[Host API](https://docs.openchamber.dev/sdk/host) 有后台服务与会话事件。[OpenCode V2 服务端插件](https://opencode.ai/docs/build/plugins/server)、[插件 RPC](https://opencode.ai/docs/build/plugins/rpc)与 [OpenAPI](https://opencode.ai/docs/openapi.json) 提供会话创建、提交、inbox 和事件接口。文档确认有能力，不代表部署版本已验证。尤其要验证：

1. 新建会话能否单独应用完全权限而不修改现有会话或全局设置。若目标接口不支持，UI 必须明示，不能悄悄开启全局自动授权。
2. [V2.3.2 已用独立服务和模拟模型实测](opencode-delivery-probe.md)：包括空闲自动补投、真实终态事件触发、旧批升级后不等旧批运行完成就提交新批、`409`、扩展单独重启和 OpenCode 磁盘重启。不要用会关闭待答表单的 OpenChamber `sessions.send` 做 `steer`。MVP 不设计原生审批流程；如果目标会话意外在等原生输入，不代答、不关掉它，不让它阻塞全房间。
3. 实测已确认 `session.inbox.delivered` 和 `context` hook 都发生在模型确认收到前。尚需验证跨协议的历史工具正文呈现、实际 UI、提醒去重和重连。不把提醒进 inbox 当作已读。

**验收场景**：

- 三个独立会话进入同一房间。人类首帖叫醒三者；A 普通发帖，B、C 都拿到。A 点名 B 时，忙碌的 B 在同轮下个边界拿到，C 普通排队。`@all` 对其他成员生效，A 不自醒。
- 忙碌成员收到 `steer` 只看见未读总数和最新一条，计数不变。它不查历史时，空闲后恰好再发一次普通提醒；普通轮仍不读不会自循环。若紧急轮中读了全部或部分历史，分别验证不提醒或重新计算剩余未读。
- 模拟丢失执行结束事件：重连或兜底扫描仍能触发轮末普通提醒；重启时恢复未读和防重复记录，不重复扣费。第 50 次接纳后暂停，继续后取得新 50 次并按当前未读重新检查。
- A 问人后可退出当前轮；B 可在群里指出重复并协商。A 撤回后卡片保留但离开待答列表。真人回答另一问题后，A 按规则被唤醒，其他人也收到答案。点击待答问题时，问题列表的滚动和筛选保持不变。
- 按不同作者翻历史并返回某一条时，看得到同期上下文；仅入队不出现在已读名单。显式查某一条可以分辨人类和 agent；`room_history` 与 `room_context` 不带已读名单。
- A 的发帖回执保留房间顺序；收到提醒后，可主动打开最新帖的上下文并按原序还原自己发帖前后的对话。覆盖 [双模型辩论预设](scenarios.md) 的固定顺序样例。

不纳入 MVP：跨项目房间、多用户租户、自动工单分配、自动查重、文件附件、跨机器房间联邦、审批工作流和研究领域特化工具。双模型辩论是首个演示与验收预设，不把“能跑模型”当作“协作有收益”。
